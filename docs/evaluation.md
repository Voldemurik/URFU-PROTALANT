# Система оценки качества

Ключевая часть проекта — не «чат с документами» (таких много), а измеримость:
каждая правка промпта, чанкинга, модели или поиска должна отражаться в цифрах.
Система оценки встроена в пайплайн (`techdoc eval`) и работает полностью локально.

## Почему своя, а не готовая

Готовые фреймворки (RAGAS, DeepEval, TruLens) ориентированы на английский, по
умолчанию используют облачные модели-судьи и оценивают в основном текст ответа.
Для промышленной документации на русском важны другие вещи: нашёл ли поиск
*тот самый* документ, сохранились ли числа и коды, сослалась ли модель на
источник и, главное, отказалась ли отвечать, когда ответа в документации нет.
Все метрики ниже считаются без сети; LLM-судья — локальной моделью.

## Оценочный набор

JSONL-файл, по одному вопросу на строку (`data/eval/sample_qa.jsonl` — учебный пример):

| Поле | Назначение |
|---|---|
| `question` | вопрос инженера в свободной форме |
| `reference_answer` | эталонный ответ, составленный по документу |
| `relevant_docs` | какие документы содержат ответ — их `doc_id`, то есть путь относительно каталога, переданного в `techdoc ingest` (для `data/sample_docs` это просто имя файла) |
| `must_include` | обязательные факты — коды, числа, термины, которые обязаны быть в ответе |
| `answerable` | `false` — вопрос-ловушка: ответа в документации нет, правильно отказаться |
| `tags` | тема, тип вопроса — для срезов по категориям |

Сбор боевого набора: 100–300 вопросов, составленных вместе с инженерами
партнёра по реальной документации; 10–15 % ловушек; часть вопросов — на два
документа сразу (проверка объединения источников). Отложенная выборка не
используется при дообучении.

## Метрики по слоям

### 1. Поиск — нашли ли нужное

| Метрика | Формула | Что означает |
|---|---|---|
| `retrieval/recall@k` | \|найдено ∩ релевантно\| / \|релевантно\| | доля нужных документов среди top-k фрагментов |
| `retrieval/hit_rate` | 1, если хотя бы один релевантный в top-k | «есть ли шанс ответить правильно» |
| `retrieval/mrr` | 1 / ранг первого релевантного | насколько высоко стоит нужный документ |

Если поиск не находит документ, генерация уже не спасёт — поэтому эти метрики
смотрят первыми.

### 2. Ответ — точность и полнота

| Метрика | Формула | Что означает |
|---|---|---|
| `answer/token_f1` | F1 по содержательным токенам ответа и эталона (стоп-слова убраны, ё = е) | лексическая близость к эталону |
| `answer/must_include` | доля фактов из `must_include`, найденных в ответе (регистр, ё/е, `0,5` = `0.5` не различаются) | сохранились ли коды, числа, единицы |

Token-F1 — грубая метрика (перефразированный верный ответ получит низкий балл),
поэтому основной показатель точности — покрытие обязательных фактов.

### 3. Ссылки — на что опирается ответ

| Метрика | Формула |
|---|---|
| `citations/precision` | доля процитированных документов, которые релевантны |
| `citations/recall` | доля релевантных документов, которые процитированы |
| `citations/answered_with_citation` | доля ответов, где есть хотя бы одна ссылка `[n]` |

### 4. Галлюцинации — чего в документации нет

| Метрика | Что означает |
|---|---|
| `hallucination/trap_refusal_rate` | доля вопросов-ловушек, на которых модель честно отказалась (цель → 1.0) |
| `hallucination/false_refusal_rate` | доля обычных вопросов, на которых модель отказалась зря (цель → 0.0) |
| `judge/faithfulness` | по оценке LLM-судьи: доля утверждений ответа, подтверждённых контекстом |
| `judge/completeness` | по оценке судьи: насколько полно покрыт эталон |
| `judge/hallucination_rate` | 1 − faithfulness |

Две первые метрики считаются без всяких моделей и не подвержены субъективности
судьи; это «жёсткий» показатель. LLM-судья (`--judge`) получает вопрос, контекст,
эталон и ответ и возвращает JSON с оценками и списком неподтверждённых утверждений.
Судья — более мощная модель.

## Бейзлайн и первый эксперимент

Чтобы понимать, что даёт LLM, есть экстрактивный бейзлайн: ответ = текст самого
релевантного фрагмента. Поиск — `HashingEmbedder` + BM25, без нейросетей, учебный
набор из 13 вопросов (`reports/baseline_offline_extractive.md`).

Первый же эксперимент показал, зачем нужна система оценки. В первой версии
индексировался только текст фрагмента; затем к индексируемому тексту добавили
название документа и раздела (`Chunk.index_text()`) — вопросы часто содержат имя
оборудования или раздела, которых в самом фрагменте нет:

| Метрика | Только текст | Текст + заголовки | Комментарий |
|---|---|---|---|
| retrieval/recall@k | 1.000 | 1.000 | учебные вопросы лексически близки к документам |
| retrieval/mrr | 0.909 | **1.000** | нужный документ стал первым во всех случаях |
| answer/must_include | 0.455 | **0.682** | лучший фрагмент чаще содержит сам факт |
| citations/precision | 0.818 | **1.000** | |
| citations/recall | 0.773 | **0.955** | |
| hallucination/trap_refusal_rate | **0.000** | **0.000** | бейзлайн не умеет отказываться — здесь LLM должна дать главный выигрыш |

## Ограничения

- Token-F1 занижает оценку перефразированных ответов.
- Метрики ссылок считаются на уровне документов, а не фрагментов: следующий шаг —
  разметка релевантных фрагментов (`relevant_chunks`).
- LLM-судья может ошибаться; его оценки — вспомогательные, «жёсткие» метрики важнее.
